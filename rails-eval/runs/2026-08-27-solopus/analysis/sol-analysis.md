## 2. BEHAVIOR

### Profiling approach
- Primary: RSpec's own `--profile` (via the benchmark scripts) + "Finished in" execution time with fixed seed 12345. Run 1 announced "RSpec profiling and TestProf event profiling" but never actually used EVENT_PROF/RD_PROF — diagnosis came from reading `rails_helper.rb` hooks (inline Sidekiq, `redis.del(redis.keys)`) plus targeted greps. Run 3 used test-prof's **FactoryProf** (`FPROF=1`), first via `RUBYOPT`, then — after two load-order failures — via a permanent env-gated hook in `rails_helper.rb` (`if ENV['FPROF'] require 'test_prof' ...`). No stackprof, no custom Ruby timers beyond `date +%s%N` wall-clock wrappers (built after both `/usr/bin/time` and the shell `time` keyword turned out to be missing).
- Measurement discipline: strong. Fixed seed everywhere; identical file sets before/after; sequential reruns when it suspected DB contention polluted the parallel baseline (run 1 steps 8, 18: "rerun the exact same fixed-seed chunks sequentially to avoid the database contention present in the initial parallel baseline"); run 2 step 16 temporarily restored the pre-optimization helper for a controlled 916-example baseline and restored the optimized one after; run 1 step 18 used `trap 'cp ...' EXIT HUP INT TERM` to guarantee helper restoration. Second-seed run (RSPEC_SEED=9876) in run 1 step 23 "to catch ordering/mode leakage".

## 3. OPTIMIZATIONS FOUND/APPLIED

### Run 1 (spec/models, config-level) — result 28.3% (core 36.2%, concerns 23.3%), 475-example sample, 28.86s → 20.70s
- Applied: global `config.before { Sidekiq.testing!(:inline) }` replaced with per-example mode — fake for `type: :model` unless `:inline_jobs` metadata; other types stay inline. 3 opt-in tags: `user_spec.rb` `#mark_email_as_confirmed!` describe, `email_subscription_spec.rb` Callbacks describe, one `it 'sends email to target account user'` in `admin/account_action_spec.rb` (narrowed from the whole `#save!` describe).
- Tried & reverted: lifecycle-aware Redis teardown (skip `KEYS`/`DEL` unless `Thread.current[:redis]` set, checkin to pool) — measured a regression, and `with_redis` can bypass the thread-local; reverted.
- Identified, deferred: per-example `redis.keys`+`DEL` cost (picked up in run 2); route reload checks, cache clearing, DNS stubbing noted as global work but not pursued.

### Run 2 (spec/requests, config-level) — result 22.9% on full API v1 (916 ex, 59.34s → 45.76s); 26.1% on the 402-example sample
- Applied: (1) fake Sidekiq extended to `type: :request` (`[:model, :request]`); 7 opt-in sites — whole-file tags on api/v2 notifications, v2 notifications/accounts, v1 timelines/home, v1 conversations, v1 notifications, v1 admin/account_actions (after learning shared_examples metadata doesn't propagate), plus one context in statuses/favourites and one `it 'creates a report'` example. (2) `redis.del(redis.keys)` → `redis.flushdb` in the global after hook.
- Investigated & rejected: Sidekiq per-worker inline test modes (unsupported/brittle).
- Identified, deferred (documented as next hotspot): `spec/requests/cache_spec.rb` — ~21s / 258 generated examples with intentional repeated requests; "Optimizing it safely likely requires restructuring examples, so it was left unchanged in this phase."
- Validation: 1,875 request examples green in bounded groups + 122 model examples as Redis regression check.

### Run 3 (factories/Fabrication) — result 23.7% combined sample (core models 7.41→5.95s = 19.7%; api/v1/statuses requests 5.19→3.67s = 29.3%)
- Applied: removed `user` fabricator's `after_create { 2.times { Fabricate(:login_activity, ...) } }`; removed `status` fabricator's `after_create { Fabricate(:bookmark, ...) }` (which silently built a *second* full account+user+2-login-activity graph since the bookmark's account isn't the status author); replaced Faker identity defaults with deterministic sequences (`account#{i}` → fixed to `fabricated_user#{i}` after reserved-username collisions; `user#{i}@example.com`); added env-gated FPROF hook to rails_helper; added guard comments in both fabricators.
- Identified, deferred: FactoryProf still shows factories at ~50–68% of execution (514 calls / 3.97s of 5.88s model sample; 339 calls / 1.85s of 3.84s request sample) — "account/status creation as a useful future profiling target, but those remaining records are part of the requested object graphs."
- Validation: 1,795 model + 1,877 request examples green directory-by-directory; DB explicitly cleaned after the `rails runner` smoke test polluted it (`DatabaseCleaner.clean_with(:deletion)`); spec/fabrication suite not run (see above).

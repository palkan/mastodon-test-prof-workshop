## Insights

- **Luna is worse than "lazy": it under-delivers and knows it.** 1–2 ideas per phase, stopped short of targets, and wrote in its own docs that it *"does not substantiate the requested 30% improvement"* — then submitted anyway. It never questioned Sidekiq inline mode (the headline lever). Its one factory "extra" (Faker→`username#{i}` sequences) **broke 6 `Account::Search` examples** — it never re-ran the full models suite after the change. Honest, extremely cheap, but shallow: profile depth = RSpec `--profile` only, despite grepping test-prof in the Gemfile and moving on.
- **Kimi's step count is measure-first discipline, not flailing** (hypothesis "reads everything instead of experimenting" — partially confirmed, with a twist). The steps went to hand-built instrumentation (custom SQL/hook/Fabricate profilers, stackprof boot shims, 3–5 retries each), background-run babysitting (`nohup … sleep … tail` to dodge tool timeouts), multi-seed re-measurement, and exhaustive gem-source reading (sidekiq, fabrication, AR internals). It kept optimizing past targets in phase 3. Weaknesses: skipped `spec/fabrication` validation in the clean run; picked `:warn` over `:fatal`; dismissed flushdb after a micro-benchmark that missed the aggregate effect.
- **Grok had the best process end-to-end**: fixed-seed A/B for every change, experiment-and-revert before committing, read its own phase-1 docs as the *second command* of phases 2 and 3, ran fabrication specs after factory edits, self-recovered from a polluted test DB. Its phase-1 notes pre-identified the phase-3 factory targets. Main gap: never re-ran the full suites after phase 3 — its "≥20%" claim was extrapolated from a hot slice (our measurement vindicated it).
- **Memorization is doing real work here.** The planted regressions are reversals of actual upstream Mastodon test setup, and both Grok and Kimi recognized Mastodon instantly ("This looks like Mastodon" — step 4 of every Grok phase). Grok's fixes restore upstream almost verbatim (`:inline_jobs` tag name, `before_all` in cache_spec); Kimi explicitly reasoned *"In upstream, there is no after_create bookmark hook (I believe)"*. Part of the signal is "does the model remember Mastodon's test suite" — worth deciding whether that's signal or leakage (see stage-2 design note below).
- **Between-session timing drift is real even in one environment.** All sessions shared the same dip environment, yet Grok's in-run baseline (148.9s) sits ~13% above the four other measurements of the same code (~130s), while its optimized time matches ours exactly. Cause unidentified (live host, hours apart) — which is precisely the point: any grading that compares a time measured *now* against a baseline measured *in another session* inherits that drift. Log I/O still dominates the real levers here (Kimi's `log_level = :warn` alone bought ~63% on models).
- **Divergent root-causing of the same plant**: for SQL-logging overhead, clean Kimi masked it with `log_level = :warn`; maybe-unfair Kimi found the sharper cause — `fetch_replies_concern_spec.rb` sets `ActiveRecord.verbose_query_logs = true` at load, leaking `BacktraceCleaner` work (~31% of wall) into randomly-ordered runs — and fixed it with a reset hook (42% gain). Grok's `:fatal` masks it too. A great discriminator between "mask the symptom" and "find the cause".
- **TestProf recall**: Grok recommended FPROF/EVENT_PROF in its docs but never ran them (Benchmark.measure micro-benches instead); Kimi used the full kit (RD_PROF, EventProf, FPROF, stackprof) plus custom tooling; Luna used none. Only Grok used `before_all`.
- Docs discipline (instructed): all three maintained docs/ notes and read them back at later phases — cross-step memory via files works.

| **Total** | **1.7 / 2** | **4.8 / 5** | **2.1 / 2.75** |
| **Reward** | **0.085 / 0.10** | **0.84 / 0.85** | **0.705 / 0.7375** |

(The judge pass predates the plan's 9th feature, *Faker in factories*, so both columns above grade the original 8; with it, runtime rewards become 0.15 / 0.85 / 0.79 — the Faker diffs are unambiguous, so a judge would score it identically.)

Findings:

- **No hallucinated credit.** Every judge deviation is an *under*-credit; it never awarded a feature the runtime probes disproved. Ranking is preserved exactly; magnitudes drift by 0.3–0.65 feature points (≤0.03 reward).
- **The deltas concentrate precisely where execution semantics decide the outcome.** The judge discounted (with stated low confidence) exactly the three things a diff cannot settle: (a) whether Kimi's `around Sidekiq::Testing.inline!` opt-in survives the type-scoped `before` hook setting `:fake` — it flagged Sidekiq 8 mode-state precedence as unverifiable by reading (runtime: green suites, including the tagged inline-dependent examples, settle it); (b) whether a type-scoped fix "counts" when the plan's probe location determines the derived `:type` (grok 0.8, kimi 0.6, luna's flushdb 0.7 — the runtime probes, placed under model/request metadata per the plan's intent, award full credit); (c) partial-credit policy where the plan is silent (kimi's `:warn`: judge 0.5 vs our 0.75).
- **Score-version instability is the real cost.** The judge invents its own fractional policy wherever the plan under-specifies (probe location, `:warn` vs `:fatal`, scoped vs global). Two honest judges could defensibly emit 4.8 or 5.0 for grok. Runtime probes plus an explicit fraction table make the same decisions once, deterministically.
- **Judge confidence is usable routing signal**: every mis-scored feature was self-marked medium/low confidence. A practical hybrid: accept high-confidence judge scores, escalate low-confidence features to runtime probes.
- The judge also could not recover the intended "known spoiled factories" list for the `Fabricate.build` feature from the diffs (it guessed different candidates than the planted ones) — the checklist must name them explicitly for any grader, human or model.

What only diff-reading (judge or rules) can see — keep it for these: scope compliance (Grok edited `app/services/webhook_service.rb` in a "configuration-only" phase; `Rack::Attack.enabled = false` + HttpLog skip are behavioral trade-offs invisible to feature probes), the spec-diff budget, "specs must read the same" preservation, and maintenance smells (Kimi's `FabricateHelpers` duplicating fabricator defaults). And any diff-only grading is speed-blind and correctness-blind — it cannot know that Luna's innocuous-looking Faker→sequence diff breaks 6 search examples.

Conclusion: judge-from-diff is safe for *ranking* and honest about its uncertainty, but under-credits wherever hook ordering, probe placement, or partial-credit policy matter — all decided by one executed example. Features by runtime probes; policy/scope/budget by diff review (judge confidence deciding what escalates).

## Suggested improvements to deterministic verification

1. **Measure old and new under one protocol.** Sum-of-separate-runs (299.6s) vs one combined process (415.0s) differs by 38% on the same baseline code (log growth + GC). The encrypted `rspec-baseline.json` must be produced by *exactly* the command the verifier will run later (`rspec spec/models spec/requests --seed <S>`), same container, same session.
2. **Grade on same-session ratios, and soften the step gates.** Observed ~13% between-session drift (Grok's 148.9s baseline vs the ~130s consensus) means a stored setup-time baseline is a stale denominator. Strongest fix: at verification time, check out the pre-agent revision and run baseline + candidate back-to-back in the same session — drift cancels in the ratio; keep the encrypted setup-time artifact only as a fraud cross-check. Take each side as median-of-N (N=2–3 suffices; our repeats were ±1% within a session). And still soften the gate: margin (pass ≥25% when targeting 30%) or fractional steps 1–2 (`min(improvement/0.30, 1)`), halting only on ≤0 improvement or fraud.
3. **Correctness is a precondition, not a check.** Require 0 failures on the graded suites (and `spec/fabrication` after the factory step) before any speed grading — that alone catches Luna's broken final state. Also compare *example counts* against baseline (`--dry-run` count) to catch silently skipped specs; it's a stronger anti-fraud signal than diff size.
4. **Fill the last missing feature slot** (plan says 10, defines 9) with an organically-discovered bottleneck: the `verbose_query_logs` leak from `fetch_replies_concern_spec.rb` — probe `ActiveRecord.verbose_query_logs` inside a spec (middleware overhead — `Rack::Attack.enabled` / HttpLog loaded — is the runner-up). The Faker feature's probe is straightforward: wrap `Faker::Internet.user_name`/`.email` and count calls during `Fabricate(:user)` + `Fabricate(:account)` (baseline 4 → 0 when fixed). Grade `log_level` fractionally (`:fatal` 1.0, `:warn` 0.75, else 0) since `:warn` already eliminates the I/O.
5. **Runtime probes work — ship them as `verification_spec.rb`.** All eight features verified deterministically in ~15 examples: `Sidekiq::Testing.inline?` under model/request metadata; `Rails.logger.level`; RedisClient middleware capturing cleanup commands (`flushdb` vs `keys`+`del`); record-count deltas for cascades; INSERT-count subscriber around `Fabricate.build`; BCrypt call counter around `Fabricate(:user)`; `file_meta` presence for paperclip. For `before_all`: `FPROF=1 rspec -r test_prof spec/requests/cache_spec.rb` factory total is a clean discriminator (baseline 4139 → Grok 19; threshold: `< example count`). One caveat: Fabrication auto-downgrades nested creates inside build sessions, so `Fabricate.build` persistence probes show 0 even on the regressed code — verify that feature via the *create*-path insert count (or statically) instead.
6. **Harness hygiene** (the maybe-unfair lesson): reset workspace `tmp/`, **system `/tmp`**, `log/`, and `docs/` between runs; drop `rails-eval/` from the agent-visible checkout (it's tracked on the baseline branch — nobody peeked this time, but it's an answer key sitting in the workspace); keep the emptied `.git` (it worked). Fix the instruction templating bug that produced `instruction..md` and assert the rendered prompt is not a path.
7. **Enforce limits at run time.** Kimi's phase 3 (155 steps, $6.24) would have been cut off at 100/$5; unlimited runs make cost a hidden confound in cross-model comparison. Record per-phase usage in the merged result (done here in `metadata.per_step_usage`).
8. **Decide the memorization question.** Since plants are reversals of upstream Mastodon code, models with Mastodon recall partially "remember" the answer. Either accept it (measuring Rails-ecosystem knowledge is a stated goal) or perturb the plants so upstream memory mismatches (rename tags, move hooks) to isolate diagnosis skill.

## Positioning: what this benchmark adds over CursorBench / TerminalBench / DeepSWE

A recurring critique: *"most code benchmarks converge to the same result; CursorBench/TerminalBench/DeepSWE already cover this, and it's nearly saturated."*

What those suites measure: SWE-bench-family (incl. DeepSWE as an RL-trained solver on it) measures *issue → patch that passes hidden tests* — binary, mostly Python, public GitHub data with contamination pressure. TerminalBench measures *multi-step shell/tool competence to a verifiable end state*. CursorBench measures *agentic edits in real repos accepted by tests*. They correlate because they sample the same axis: binary functional correctness of a patch, single session, cost-blind. The convergence claim is true **within that axis**.

This suite (stage 1: `ai-evals` atomic Rails tasks; stage 2: multi-step campaigns like this one) samples different axes — and this run is a concrete counterexample to convergence:

1. **Non-functional objective, fractional reward.** "Make it faster without breaking it," with correctness as a constraint and continuous grading. GPT-5.6-luna — presumably respectable on pass-rate suites — scored 0.15 here while Grok hit 0.85. A binary harness cannot even express what happened (Luna's suite *runs*; it's just slow and subtly broken).
2. **Not saturated.** Top score 0.85, with three whole feature classes (Paperclip stubbing, `Fabricate.build` restoration, BCrypt) untouched by every model. The headroom is empirical, not aspirational.
3. **Multi-session memory.** The docs/-knowledge-file protocol measures whether an agent builds and *reuses* knowledge across runs (Grok re-read its own notes as the second command of each phase; its phase-1 notes pre-planned phase 3). No mainstream code benchmark tests cross-session carry.
4. **Diagnosis vs masking.** The same plant was "fixed" two ways — `log_level = :warn` (mask) vs finding the `verbose_query_logs` leak in one spec file (root cause). Fractional feature grading can price that difference; pass/fail cannot see it.
5. **Economics as a first-class axis.** A 170x cost spread ($0.06 vs $10.76) and 6x step spread for adjacent final quality. "Benchmarks converge to the same result" collapses once results are priced — and the default limits (100 steps, $5/trial) make efficiency part of the score.
6. **Ecosystem depth.** Rails/TestProf/Fabrication/Sidekiq-testing semantics that Python-dominated suites structurally can't probe — e.g. knowing `Sidekiq.testing!(:fake)` vs `:inline`, or that `before_all` exists. The TestProf-recall spread (Kimi: full kit; Grok: recommended but never ran it; Luna: none) is invisible in a pass rate.

Honest concessions: benchmark design *is* hard, and this round hit it directly — the 30% time gate proved fragile against between-session drift, n=1 per model, and upstream-Mastodon memorization is a real confound (see improvement #8). But where this suite's *ranking* merely correlates with general capability, the deliverable isn't the ranking — it's the orthogonal diagnostics (cost discipline, memory reuse, root-cause vs mask, honesty about missed targets) that pass-rate benchmarks discard.
